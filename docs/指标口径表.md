# Olist 项目 · 指标口径表

> 用途：统一 Python 分析、SQL 取数、Agent 问答三处的计算口径，避免简历/面试时出现同一个指标两个数字。
> 口径版本：v1.0

## 一、基础口径

| 指标 | 定义 | 计算方式 | 数据源 |
|---|---|---|---|
| 有效订单 | 已送达且时间合法 | `order_status='delivered'`，实际送达与预计送达非空，且送达时间 ≥ 下单时间 | orders |
| 订单数 | 去重订单 | `COUNT(DISTINCT order_id)`；明细表一单多行，不能 `COUNT(*)` | order_items |
| 商品销售额 | 商品金额合计 | `SUM(price)`，过滤 `price > 0` | order_items |
| 运费收入 | 运费合计 | `SUM(freight_value)` | order_items |
| 平均运费 | 每单平均运费 | 运费合计 ÷ 去重订单数（约 22.79 元/单） | order_items + orders |
| GMV / 订单总金额 | 商品 + 运费 | `SUM(price + freight_value)` | order_items |
| 客单价 | 每笔订单平均金额 | GMV ÷ 去重订单数（**不是按行求均值**） | orders + items |
| 品类 | 中文品类名 | 葡语字段 `product_category_name` 经翻译表映射；映射不到保留原值，不丢弃 | products + 翻译表 |

## 二、履约口径

| 指标 | 定义 | 计算方式 | 注意 |
|---|---|---|---|
| 配送天数 | 下单到签收 | `DATEDIFF(实际送达, 下单时间)`，仅已送达订单 | 单位：天，按订单 |
| 平均配送天数 | 订单级均值 | 已送达订单的配送天数均值（先降到订单粒度再求均值） | 按行求均值会被多件订单拉偏 |
| 延迟订单 | 晚于承诺时间 | `实际送达 > 预计送达` | 未送达订单**不计入**延迟，也不计入分母 |
| 延迟率 | 延迟订单占比 | 延迟订单数 ÷ 已送达订单数 | 分母不含未送达，与「全部订单」口径差约 1 个百分点 |

## 三、评价口径

| 指标 | 定义 | 计算方式 | 注意 |
|---|---|---|---|
| 平均评分 | 订单评分均值 | 有评价订单的 `review_score` 均值 | 一个订单多条评价只保留一条（Python 取首条，SQL 用 `MIN` 近似，差异 <0.1pp） |
| 差评订单 | 评分 ≤ 2 | `review_score IN (1,2)` | 1~2 分统一算差评 |
| 差评率 | 差评占比 | 差评订单数 ÷ **有评价订单数** | 未评价订单不进分母；用全部订单作分母会低估 |
| 品类差评率排名 | 品类间比较 | 同上，按品类分组 | 样本 < 30 的品类不参与排名 |

## 四、用户口径

| 指标 | 定义 | 计算方式 |
|---|---|---|
| RFM-R | 最近一次下单距今天数 | `DATEDIFF(数据截止日, 最后下单日)`，越小越好 |
| RFM-F | 下单次数 | 去重订单数 |
| RFM-M | 累计消费 | 用户 GMV 合计（含运费） |
| RFM 打分 | 五分位 | `NTILE(5)`；R 反向计分。并列时以 `customer_unique_id` 为次级排序键，保证可复现 |
| 客户分层 | 6 类 | 高价值 / 潜力 / 一般 / 新客 / 流失 / 流失高价值（规则见 SQL 第 6 条） |
| 新客 / 老客 | 当月是否首单 | 当月 = 用户首单月份 → 新客，否则老客 |
| 复购率 | 下过 2 单及以上的用户占比 | 复购用户数 ÷ 总用户数 |
| 次日/30 天留存 | 首单后 30 天内是否再下单 | 首单后 1~30 天内有订单 → 留存 |

## 五、易错点（面试高频追问）

1. **一单多行**：`order_items` 一单多商品，直接 `AVG(金额)` 得到的是「件单价」而非客单价。必须先把金额聚合到订单粒度，再求均值。
2. **未送达订单**：既不是延迟也不是准时，必须从延迟率分母中剔除；否则延迟率会被稀释（统一口径 8.1%，旧行级口径 7.9%）。
3. **未评价订单**：差评率分母应为有评价订单，否则差评率被低估。
4. **类目映射**：早期版本用了英文字段导致「其他类目」占 89%，改为葡语原字段 + 翻译表后降到约 10%，这是本项目修掉的一个 P0 问题。
5. **金额定义**：Monetary / GMV 均含运费。只看 `price` 会漏掉约 16% 的金额（RFM 均值 141.62 → 165.17）。
6. **排序并列**：RFM 中 93% 用户只下过 1 单，F 大量并列；不固定次级排序键时，不同引擎的分层结果会漂移。

## 六、口径统一记录（v1.1）

2026-11 已把 Python、SQL、Agent 三处统一为「订单粒度 + 有评价/已送达为分母」，主要指标变化：

| 指标 | 旧口径（商品行级） | 统一后（订单级） |
|---|---|---|
| 平均评分 | 4.08 | 4.16 |
| 差评率 | 14.65% | 12.80% |
| 延迟率 | 7.91% | 8.11% |
| 平均配送天数 | 12.01 | 12.09 |
| 30 天以上差评率 | 63.6% | 65.3% |
| 办公家具差评率 | 25.45% | 21.95% |
| 办公家具平均评分 | 3.52 | 3.64 |

实现方式：

1. `scripts/analysis.py` 新增订单粒度基础表 `order_base`（一单一行，金额与延迟先聚合到订单）
2. 评价、延迟类指标先降到订单粒度再算比率，不再按商品明细行加权
3. `output/csv` 与 7 张图表已按新口径重跑，`olist_agent/data` 同步更新
4. Agent 评测集的 20 道标准答案同步改为新口径，复测通过

> 面试说明：如果被问"为什么改了数字"，答案是——旧版用商品行作分母，一单多件会把大件品类的差评率放大；统一为订单粒度后，办公家具从 25.45% 修正为 21.95%，结论方向不变（仍是差评最高的主流品类），但数值更经得起复核。
